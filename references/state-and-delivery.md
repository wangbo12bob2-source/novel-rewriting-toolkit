# 状态、接续与交付

使用轻量文件，不需要任务服务或数据库。沿用有效的既有目录和格式；新项目可采用下列最小布局，只有确实需要才新增旁档。

```text
项目目录/
  project.md                 当前约定与授权
  progress.md                当前阶段、版本、完成范围、问题和下一步
  input/                     原稿副本、提取文本与导入记录
  source_units/              按原序号拆分的原文
  analysis/                  原稿事实与编辑分析
  design/                    新设定、名称登记、分集／章计划
  body/                      当前版完整正文
  continuity.md              剧情相关的实际状态与变更
  review/                    审稿及问题闭环
  versions/                  修改前版本
  delivery/                  从当前版导出的文件
```

不要为了“齐全”创建空文件或占位状态。旧工程的AGENTS.md或其他长期指令若与最新授权冲突，要同步有效入口，不只在聊天里说明；历史报告保留日期与范围。

## 唯一当前入口

progress.md指向当前版本和各权威源，记录实际完成范围、待解决问题、下一步及最近用户范围变化。project.md是约定依据，正文是已写剧情的事实依据；大纲是计划，修订日志解释有意变化。

正文／交付／摘要版本不一致时先查明来源，不自动覆盖。第二版工作稿未完成时，第一版交付仍标第一版；不能把部分修订的目录当作新版完整成果。

## 连续性记录

只跟踪会影响后文的状态：

| 对象 | 记录 |
|---|---|
| 时间 | 故事日与昼夜、连续行动、明确间隔；集号不是天数 |
| 人物 | 位置、目标、关系、伤势、谁知道哪些事实 |
| 物件 | 所在处、持有者、交接、损毁、复制与归还 |
| 能力 | 当前可用范围、已消耗次数、恢复条件及实际展示位置 |
| 问题 | 正文已提出什么，哪里回答，哪些仍未兑现 |

每段写完更新实际变化。结构修改时列出“变更事实→影响范围→待同步文件”，核对后再标完成。更改一个日期或物件流向时，搜索后文回指并回读相关场面；不能仅改索引。

## 接续

新会话读项目约定、当前进度、适用设定、相关角色状态、上一段摘要和当前任务对应正文。事实有疑问就回读原段，不猜。

按自然单元或重大转折落盘。无需猜测800K等固定上下文预算；当环境提示容量将尽、工具连续失败或质量明显下降时，保留已完成文件，记录精确断点、未完成动作和下一步。

被中断后先核对磁盘，不能只信聊天里的“已完成”。用户明确暂停立即停止；用户要求继续则从有效断点推进。不要通过写ALL_DONE之类标记把未写正文变成完成。

## 验证工具

仓库当前没有内置导入器、命名检查器或导出器；可使用环境已提供的工具，或在用户项目内编写确有必要的小助手。先确认它存在、输入适用并实际运行，再报告结果。

确定性检查可覆盖：集／章编号与标题、场次、登记名、未完成标记、明确的能力计数和引用、源文件一致性、导出全文。名称扫描区分专名、别称和普通词，不使用“所有旧名汉字禁用”。

这些检查发现的只是它们覆盖的问题。[编辑复核](editorial-review.md)仍单独进行。没有必要为手册执行开发Python包、模型代理、调度系统或质量打分服务。

## 版本与导出

大修前保留完整可回读版本和对应审稿意见，记录当前版从何而来。新导出用清楚的版本名，保留旧交付；标明未写或未修部分，不混成一个看似完成的合订本。

按用户要求提供Word、Markdown或纯文本，正文不混入自评、提示词和调试日志。导出后回读核对顺序、集／章标题和全部正文；只检查数量可能漏段。未做视觉排版检查时，不声称排版已全部验证。

用户未要求上传或发布时只交付本地结果。Git仓库只收Skill和允许公开的辅助资料，私有素材、样本、正文和运行记录不提交。
